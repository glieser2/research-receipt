- No custody, token transfer, investment transaction, or automatic payment.
- Owner locks a non-zero author address, criteria and 1–6 buyer-approved repository roots; author alone submits a revision. Only owner or author verifies evidence or evaluates the current revision. Public reads do not grant mutation rights.
- Each revision stores at most one assessment and one evidence snapshot. Content fingerprints ignore report names/version labels and normalize source/citation order; any replay across the bounded history is rejected. Paraphrased equivalent content is not fully detectable.
- Source URLs use one fixed public HTTPS origin and full Git commit; malformed, private, mutable, credentialed, query-bearing and encoded paths are rejected.
- Sources must match exact SHA-256 and byte length. Missing, changed, unavailable or undecodable evidence never becomes a positive finding.
- Raw source fetch occurs through GenVM web facilities. The application does not control that service's DNS/TLS/redirect implementation; runtime guarantees must be checked before expanding the origin policy.
- The 16 KiB limit is checked after the response arrives, not a network-layer hard download cap. A repository root and content hash fix source identity/bytes but do not prove official publisher authority, publication date, deployed bytecode provenance, external truth or code correctness.
- V5 `report_body` must exactly equal normalized statements joined by one newline in locked-criterion order; extra free text, surrounding whitespace and report-wide substitutes for missing claims are rejected. No claims requires an empty body. Titles and external report links are not accepted report content. A prompt contains only the current criterion/statement, its selected verified sources and protocol/chain/date metadata; other claims and full report text are excluded. These values remain untrusted data. Strict enums/references are validated, but prompt injection and semantic errors remain possible.
- Policy v5 requires an explicit `evidence_requirement` per criterion: `fact_required` or `scoped_unknown_allowed`. Missing/unknown values are rejected, not silently defaulted. The field is excluded from model prompts; paired inputs differing only in this field produce identical prompt bytes. The model classifies evidence, and code derives delivery status afterward.
- Model evidence labels are `SUPPORTED`, `CONTRADICTED`, `SCOPED_UNKNOWN`, and `NOT_ESTABLISHED`. Missing claims become `NOT_ESTABLISHED`; a claim citing failed evidence becomes code-only `SOURCE_UNAVAILABLE` with no model call for that claim. `SCOPED_UNKNOWN` is not proof of the underlying fact. It fulfills delivery only under the buyer's explicit allowed policy; contradiction and source failure cannot be overridden.
- Both positive support and scoped-unknown disclosure require coverage of every materially requested part of the criterion. Irrelevant true details, omitted analysis or unknown text mixed with unsupported promises cannot satisfy this gate. These are model instructions and validated output boundaries, not a proof that the model always recognizes coverage correctly.
- `SUPPORTED` requires every materially requested fact to be established with none reported unknown; `SCOPED_UNKNOWN` requires at least one accurately unknown requested fact and all others established or accurately unknown. A disclaimer about deployment facts outside the criterion does not create a requested unknown. The model must judge literal negations and cannot first correct a false claim and then label the corrected claim supported.
- Stable consensus fields include evidence status, code-derived delivery status, references, source checks and aggregate verdict. Forged delivery values fail validation; matching aggregate verdicts alone are insufficient. One global format-only repair per independent invocation never resamples a legal unfavorable result; provider failures do not enter that retry path.
- V5 verification independently fetches every committed source in leader and validator, validates checks/materials and compares the complete result. Evaluation revalidates the accepted snapshot in each side and judges independently with zero source HTTP. Result agreement compares stable factual fields, not prose explanations or model confidence.
- The immutable snapshot binds policy, order/revision, spec/submission/content hashes and all indexed source commitments. Verified UTF-8 materials must exactly match bytes/length/hash; failed entries are strictly null, including unused sources. There is no author snapshot/inline-byte import API. Assessment snapshot_hash and all source checks must equal the accepted snapshot.
- Each revision gets one snapshot, including failures. A transient UNAVAILABLE result cannot be re-fetched for that same revision; first assess with the affected claims ineligible, then genuinely correct evidence/research in a new allowed revision if the order is not accepted. Do not encourage meaningless paraphrases to evade replay controls. No bounded retry mechanism was added. Evaluation failure leaves its earlier committed snapshot intact.
- Verification and assessment are separate signed transactions. The app checks a fresh wallet state, waits for finality plus successful execution/readback, preserves the stage and transaction ID across interruption, and retains unresolved writes rather than automatically advancing or resending.
- Raw documents are public inputs and appear in network execution; never submit private conversations, credentials, API keys, or account details.
- No blockchain write is labeled complete from a wallet submission or EVM receipt alone. Application requires FINALIZED and successful execution, followed by state readback.
- Studio-dev (61997) is a hosted development simulation. Its actual GenVM/model execution and protocol finality do not establish public-chain inclusion. Observed development receipts contain null block hash/number; absent public block evidence must never be invented.
- Development deployment `0xa73d09fE5f065ECa8d05b3371cDC5E91213319f1` is bound to source SHA-256 `3817bc2c658b5c5501e50b39263cd3291eaa8e6b29181110007ccb352ecb32c3`; this identity does not silently carry over to another network or changed source.
- Receipt provenance is bound to the order's loaded mode, RPC and contract, not mutable settings. Local receipts never contain fabricated transaction hashes.
- Pending writes are not blindly retried. Canceled transactions unblock only after observing CANCELED; network uncertainty retains the same ID and client reference.
- Frontend RPC choices use declared supported environments; public Bradbury tooling separately checks chain ID, genesis and protocol registry addresses. SDK/runtime versions, fees and deployment must be verified per environment.
- The hosted app stores local walkthrough records in the visitor's browser. It is not a multi-user server database or backup service. Canonical live records reside in the selected contract.
- `run_nondet_default` uses the pinned SDK's additional validator sandbox. Callbacks capture in-memory JSON and stateless helpers rather than contract storage. Stub tests do not simulate that sandbox; a bounded successful development evaluation does not prove all adversarial or public-chain properties.
- Python tests stub GenVM; TypeScript transaction tests mock the SDK. These do not prove real consensus, wallet integration, fee sufficiency or blockchain settlement. Separately, actual development execution and final-state readback observed negative/corrected-positive outcomes, hash-mismatch failure, unauthorized author submission, duplicate-assessment/content rejection and a successful browser workflow. The [E2E evidence](docs/evidence/studio-e2e.json) is bounded development evidence, not exhaustive security or public-chain proof.
- The Studio deployment helper creates a fresh disposable account in memory and uses only the official Studio-dev simulation faucet after checking chain ID. It does not read `RR_PRIVATE_KEY` or use a user wallet. Source-upload acknowledgement is required; rerunning it deploys a new contract and updates frontend configuration. This mechanism is not supported as public Bradbury funding.
- Historical public Bradbury v1 deployment at `0x503b620680306533D43D57a859aB308eE9a9F7e1` has [independent deployment proof](docs/evidence/bradbury-deployment-independent.json). V2 at `0xEE2F34aF1ef90938341a95B466769C92A96E61A8` has [separate deployment proof](docs/evidence/bradbury-v2-deployment-independent.json). These verify finality, execution, source and block evidence for their own versions only. Public business E2E remains incomplete after model disagreements; v3 is frozen, undeployed, and its first real negative simulation failed semantic validation. Neither old results nor local stubs verify v3 safety. This is a public test chain, not mainnet, a production-readiness claim or external security audit.
- Protocol transaction IDs, EVM envelope hashes and block references are separate evidence. The historical v1 deployment envelope is `0xdbc727485a33a3ae57cef89e1b90491f28c2954de0f3e0df044a064e9c0e6bf1`, block `216419`; v4's own proof is separate, and Studio-dev null-block records remain development-only. A quoted protocol deposit is neither actual consumption nor an all-in fee cap.
- The user authorized public site access; anonymous HTTP verification returned 200 without redirects or credentials. GitHub publication is deferred at the user's request, and no contribution has been submitted. In-memory test-account keys are never included in source or exported evidence.
- Raw RPC/session artifacts remain local and are not publication inputs. Sanitized public evidence, frozen reviewed test inputs, MIT source fixtures/license and version archives are retained separately. Development fee allocations are not a measured production worst-case profile; an observed leader timeout and third-party appeal do not prove that 600 TU is insufficient.

This document is a threat model, not a completed production security audit. Report a reproducible issue with the precise version and public fixture; do not include secrets.
